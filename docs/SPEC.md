## 1. サービス概要

**ウラスポ**（urasupo.jp）は、北海道の「まだ静かな店」を、**その街に住む人**が
地図にピンとして残し、**90日ごとに"まだ静かか"を確認し続ける**ことで、
観光地化していない店の情報だけを保ち続けるマップサービス。

- キャッチコピー: **「北海道の、まだ静かな店を歩く」**
- 中核体験: 地図が常に下敷き。ピンを押すと一行が浮かび、そこから詳細へ沈む。
- トーン: 静けさ・ローカル感。煽らない。断定しない。
- 対象デバイス: **PC・スマホ両対応のレスポンシブサイト**（モバイルファースト）

### プロダクトの思想（UIコピーに現れている制約）

これは飾りではなく**実装すべきドメインルール**である。

1. 「掲載しているのは実在の店名と、公開情報にある事実だけ」
2. 「混みはじめた店は、検索結果の下へ静かに下がります。上に出るのは、地元がまだ静かだと答えた店だけです」
3. 「同じ街の2人が『行ったことがある』と答えると、地図に出ます」
4. 「90日ごとに、あなたに一度だけ確認が届きます」
5. 「答えないままのピンは、90日後に地図から静かに外れる」
6. 「確認を続けた人だけが、次の街を先に見られます」

## 2. ドメインモデルとルール

### 2.1 静けさステータス（quietness）

スポットは常にいずれかの状態を持つ。

| 値 | 表示 | 意味 |
|---|---|---|
| `quiet` | 静かなまま | まだ地元だけの店 |
| `crowding` | 並びはじめた | 混みはじめている |
| `touristy` | もう観光地になった | 観光地化した |

- 直近の確認（verification）の多数決で決まる。同数なら**新しい方**を採る。
- 一度も確認がなければ、投稿時の申告値を初期値とする（既定 `quiet`）。

### 2.2 ピンのライフサイクル

```
draft ──投稿──> pending ──同じ街の2人が「行ったことがある」──> published
                   │                                              │
                   └──30日間承認が集まらない──> expired            │
                                                                   │
                        published ──90日ごとに投稿者へ確認依頼──────┤
                                                                   │
                     確認に答えない まま 90日経過 ──> dormant（地図から外れる）
```

- `pending`: 地図に出ない。承認待ち一覧にのみ出る。
- 承認者の条件: **同じ街に紐づくユーザー**であること。投稿者自身は数えない。
- `published`: 地図・検索・詳細に出る。
- `dormant`: 地図から静かに外れる（削除はしない）。確認に答えれば `published` に戻る。

### 2.3 検証（verification）

- `published` になった時点から **90日ごと**に、投稿者へ確認依頼（`verification_request`）が届く。
- 回答は3択: `quiet` / `crowding` / `touristy`。
- 回答すると次の期限が90日後にリセットされ、**灯りポイント +5**。
- 期限から**さらに90日**無回答なら `dormant`。
- 過去の回答履歴はスポット詳細と確認画面に時系列で出る（例: 2025年12月 静かなまま）。

### 2.4 並び順（検索・一覧）

必ずこの優先順で並べる。

1. `quiet` のスポット（新しい確認があるものほど上）
2. `crowding`
3. `touristy`

同一ステータス内は「距離が近い順」。距離が取れない場合は「最終確認が新しい順」。

### 2.5 灯り（ポイント／バッジ）

- **灯りポイント**: 確認1回 +5、ピンが `published` になったら +10。
- **バッジ**: 「番人」（確認20回）、「冬も歩いた」（12〜2月に確認5回）、「港」（港町の街で公開ピン3件）。
  未取得バッジもグレー表示で見せる。
- 「灯りの番人 あと2件」のように、次のバッジまでの残数を出す。

## 3. データモデル（Supabase / PostgreSQL + PostGIS）

```
cities            街（札幌・小樽・函館・旭川・富良野・釧路・帯広・稚内）
  id, slug, name, name_kana, is_port, center_lat, center_lng, default_zoom

users             ユーザー（Supabase Auth と 1:1）
  id, display_name, home_city_id, resident_years, avatar_url, lantern_points, created_at

spots             店（ピン）
  id, city_id, name, address, area_name, category, lat, lng,
  status ('pending'|'published'|'dormant'|'expired'),
  quietness ('quiet'|'crowding'|'touristy'),
  reason (60字まで／なぜ自分はここへ行くのか),
  visit_frequency ('weekly'|'monthly'|'yearly'),
  author_id, photo_url,
  published_at, next_verification_at, last_verified_at, created_at

spot_tags         タグ（魚屋直営／昼が本番／現金のみ／ひとりで入れる 等）
  spot_id, tag_id

tags
  id, slug, label, kind ('accent'|'accent2'|'neutral'|'outline')

endorsements      「行ったことがある」承認（pending → published の条件）
  id, spot_id, user_id, created_at   -- UNIQUE(spot_id, user_id)

verifications     90日ごとの確認回答
  id, spot_id, user_id, answer ('quiet'|'crowding'|'touristy'), note, created_at

bookmarks         栞
  id, user_id, spot_id, planned_at (任意: 「明日 12:30」), created_at

badges / user_badges
  灯りバッジの定義と取得記録
```

### RLS 方針

- `spots`: `status='published'` は誰でも読める。`pending` は投稿者と同じ街のユーザーのみ。
- `endorsements`: 自分の行のみ挿入可。自分の投稿したスポットには挿入不可。
- `verifications`: 対象スポットの `author_id` のみ挿入可。
- `bookmarks`: 自分の行のみ読み書き可。

## 9. 監査による確定事項（2026-09-09 追補・上記に優先する）

Codex による仕様監査（`.superpowers/sdd/urasupo/codex-spec-audit.md`）と
実装後の目視検証で確定した内容。**§2〜§5 と矛盾する場合はこの §9 を採る。**

### 9.1 確認依頼（verification_request）— 新規テーブル

`/verify/[requestId]` の `requestId` はスポットIDではなく**確認依頼のID**である。

```
verification_requests
  id, spot_id, user_id(＝依頼先＝投稿者), due_at,
  status ('open'|'answered'|'missed'), answered_verification_id, created_at
```

- `published` 到達時、および回答受理時に、次の依頼を `due_at = now + 90日` で1件作る。
- 同一スポットに `open` の依頼は**常に高々1件**。
- 回答すると `answered` になり `verifications` に1行入る。
- `due_at` からさらに90日で `missed` になり、スポットは `dormant`。

### 9.2 静けさの判定 — 多数決をやめる

RLS上、確認に答えられるのは投稿者だけである。したがって多数決は成立しない。

> **現在の静けさ ＝ 最後に受理された確認の回答。確認が一度も無ければ投稿時の申告値。**

§2.1 の「多数決」は破棄する。

### 9.3 dormant からの復帰

`missed` になって `dormant` に落ちたスポットは、**投稿者が確認に答えた時点で `published` に戻る**。
この遷移は日時ベースの `nextStatus` では判定できないため、回答イベントを受ける関数を分ける。

### 9.4 期限の基準を一本化

- `VERIFICATION_INTERVAL_DAYS = 90`（公開/回答 → 次の `due_at`）
- `DORMANT_AFTER_DUE_DAYS = 90`（`due_at` を90日超過 → `missed` → `dormant`）

`DORMANT_AFTER_DAYS = 180` は**廃止**。基準は常に `due_at` からの経過日数とする。

### 9.5 並び順の完全な比較キー（§2.4 を置き換え）

```
1. 静けさ順位   quiet(0) < crowding(1) < touristy(2)
2. 距離         近い順（不明は Infinity）
3. 最終確認日時 新しい順
4. id           昇順（同値時の決定性を保証）
```

### 9.6 ポイント付与の冪等性

- 確認 +5 は **`verification_requests.id` につき一度だけ**。
- 公開 +10 は **`spots.id` につき一度だけ**（`published_at` が初めて入るときのみ）。
- Cron の再実行・回答の再送で二重加算してはならない。

### 9.7 pending の競合

- `pending` の期限は `created_at + 30日`。
- **2人目の承認が期限前に成立すれば公開が勝つ**（同時刻なら公開を優先）。
- `expired` は終端状態。以後の承認は受け付けない。

## 9.13 安全性と整合性（2026-09-14 最終レビュー領域Aの裁定・§9.1〜9.12 に優先する）

最終レビュー（Codex gpt-5.6-sol / max）で、**クライアントが Supabase の API を直接叩けば RLS の穴から
ポイント・確認履歴・承認を捏造できる**ことが判明した（`.superpowers/sdd/urasupo/final-review-A-result.md`）。
原則: **状態・時刻・ポイントを変える書き込みは、利用者に直接させない。** DB 関数（RPC）に集約し、DB が検査する。

### 9.13.1 デモモードは明示的に有効にしたときだけ
- `URASUPO_DEMO_MODE=1` を**明示**したときだけデモモード。かつ本番（`VERCEL_ENV=production` または `NODE_ENV=production`）では**無効**（設定されていたら起動時に例外）。
- Supabase の環境変数が**一部だけ**設定されている（URL はあるが anon key が無い、など）ときは例外を投げる（fail-closed）。
  「足りないからデモに落ちる」挙動は禁止。

### 9.13.2 書き込みは DB 関数（RPC）経由
以下は `security definer` の Postgres 関数にし、対象の行をロックしたうえで条件を DB が再検査する。
Server Action はこれを呼ぶだけにする。authenticated ロールからの**直接の insert/update は取り上げる**。

| 関数 | 検査すること |
|---|---|
| `create_spot` | 投稿者の `home_city_id` と投稿先の街が一致（地元の人だけ）。`status`・時刻列はDBが決める |
| `endorse_spot` | 対象が `pending` かつ期限前、投稿者本人でない、同じ街の住人。承認時刻はDBの `now()` |
| `answer_verification` | 下記 9.13.3 の回答可能条件。回答・依頼の更新・次回依頼・スポット更新・ポイントを**1トランザクション**で |
| `run_verification_cron` | service-role 専用。期限処理を行ロック下で行い、公開が期限前に成立していれば公開を優先 |

- `verifications` に `verification_request_id`（一意）を追加し、依頼を経由しない回答を不可能にする。
- `endorsements.created_at`・`spots` の状態/時刻列は DB 既定値のみ（利用者は指定できない）。

### 9.13.3 確認に回答できる時点（§9.1 の補足）
- 回答できるのは **`due_at` を過ぎた `open` の依頼**だけ（`due_at <= now`）。期限前の依頼は画面に「確認待ち」として出さない。
- **dormant からの復帰（§9.3）**: スポットが `dormant` のとき、投稿者は**最新の `missed` 依頼に1回だけ**回答できる。
  回答すると `published` に戻り、次の依頼を `now + 90日` で作る。
- 回答の受理と +5 は同じトランザクションで行い、同じ依頼では二度と受理しない（§9.6 を DB で保証）。

### 9.13.4 ポイントは台帳で管理
- `lantern_events(user_id, kind, source_id)` に `(kind, source_id)` の一意制約。確認なら `source_id = verification_request_id`、公開なら `spot_id`。
- `users.lantern_points` は台帳への記録と同じトランザクションで加算する。**利用者はこの列を更新できない**（列単位で権限を剥奪）。
- 利用者が更新できる `users` の列は、表示名・アバター・居住街・居住年数だけ。

### 9.13.5 pending の期限は絶対時刻
- `now >= created_at + interval '30 days'` で `expired`（日数の切り捨てで判定しない）。
- 2人目の承認のDB時刻が期限前なら公開が勝つ。判定はスポット行のロック下で行う。
- 期限ちょうど（`now = created_at + 30日`）の承認は期限内（§9.7 同時刻は公開優先）。DB時刻は `now()`＝各RPCのトランザクション開始時刻。

### 9.13.6 読み取りの範囲
- 未ログインでも読めるのは、公開中のスポットと、それに紐づく表示に必要な列だけ。
- `users` は表示用の列だけを出すビュー経由にする。`endorsements`・`verifications` は、読めるスポットに紐づく行か本人の行に限る。
- 表示用ビュー（`public_profiles`）と `user_badges` で見えるのは、**本人**・**公開中のスポットの投稿者**・**呼び出し者が読める pending スポットの投稿者**だけ（2026-09-16 再レビューの裁定。スポットを持たない利用者は匿名に見せない）。

### 9.13.8 権限とDB関数の書き方（2026-09-16 再レビューの裁定）
- **GRANT は既定権限に頼らず明示する**。public スキーマの全オブジェクトについて anon / authenticated から一度すべて取り上げ、必要な SELECT・栞の書き込み・RPC の EXECUTE だけを付け直す。service_role にも必要な権限を明示する。
- DB 関数は `set search_path = ''` とし、すべての名前をスキーマ修飾する（`public.spots`、`auth.uid()`）。PostGIS はマイグレーション時に実際のスキーマ（`pg_extension.extnamespace`）を調べて修飾する。public スキーマへの CREATE は anon / authenticated / PUBLIC に与えない。
- `run_verification_cron` はスポット行を `for update skip locked` で取り、ロック中のスポットは次回に回す（回答・承認と交差デッドロックしない）。cron の API は `40P01`・`40001` のとき1回だけ再実行する。
- 同時実行の統合テストは2接続（pgTAP＋dblink）で書く。
- 本番（`VERCEL_ENV=production` または `NODE_ENV=production`）の `NEXT_PUBLIC_SITE_URL` は https 必須。
- 0006 は未適用・未リリースのため、この裁定は 0006 自体を書き換えて反映する（本番DBは未作成）。

### 9.13.7 その他
- メールリンクの戻り先の origin は固定の環境変数（`NEXT_PUBLIC_SITE_URL`）から作る。リクエストヘッダー（`x-forwarded-host`）は使わない。
- `CRON_SECRET` は `timingSafeEqual` で比較する。
- RLS と DB 関数には、ローカル Supabase を使った統合テスト（匿名・投稿者・同じ街・別の街・service-role の権限表、同時回答・承認と cron の競合）を置く。
