## 1. サービス概要

**ウラスポ**（urasupo.jp）は、北海道の「まだ静かな店」を、**その街に住む人**が
地図にピンとして残し、**90日ごとに"まだ静かか"を確認し続ける**ことで、
観光地化していない店の情報だけを保ち続けるマップサービス。

- キャッチコピー: **「北海道の、まだ静かな店を歩く」**
- 中核体験: 地図が常に下敷き。ピンを押すと一行が浮かび、そこから詳細へ沈む。
- トーン: 静けさ・ローカル感。煽らない。断定しない。
- 対象デバイス: **PC・スマホ両対応のレスポンシブサイト**（モバイルファースト）

### プロダクトの思想（UIコピーに現れている制約）

これは飾りではなく**実装すべきドメインルール**である。

1. 「掲載しているのは実在の店名と、公開情報にある事実だけ」
2. 「混みはじめた店は、検索結果の下へ静かに下がります。上に出るのは、地元がまだ静かだと答えた店だけです」
3. 「同じ街の2人が『行ったことがある』と答えると、地図に出ます」
4. 「90日ごとに、あなたに一度だけ確認が届きます」
5. 「答えないままのピンは、90日後に地図から静かに外れる」
6. 「確認を続けた人だけが、次の街を先に見られます」

## 2. ドメインモデルとルール

### 2.1 静けさステータス（quietness）

スポットは常にいずれかの状態を持つ。

| 値 | 表示 | 意味 |
|---|---|---|
| `quiet` | 静かなまま | まだ地元だけの店 |
| `crowding` | 並びはじめた | 混みはじめている |
| `touristy` | もう観光地になった | 観光地化した |

- 直近の確認（verification）の多数決で決まる。同数なら**新しい方**を採る。
- 一度も確認がなければ、投稿時の申告値を初期値とする（既定 `quiet`）。

### 2.2 ピンのライフサイクル

```
draft ──投稿──> pending ──同じ街の2人が「行ったことがある」──> published
                   │                                              │
                   └──30日間承認が集まらない──> expired            │
                                                                   │
                        published ──90日ごとに投稿者へ確認依頼──────┤
                                                                   │
                     確認に答えない まま 90日経過 ──> dormant（地図から外れる）
```

- `pending`: 地図に出ない。承認待ち一覧にのみ出る。
- 承認者の条件: **同じ街に紐づくユーザー**であること。投稿者自身は数えない。
- `published`: 地図・検索・詳細に出る。
- `dormant`: 地図から静かに外れる（削除はしない）。確認に答えれば `published` に戻る。

### 2.3 検証（verification）

- `published` になった時点から **90日ごと**に、投稿者へ確認依頼（`verification_request`）が届く。
- 回答は3択: `quiet` / `crowding` / `touristy`。
- 回答すると次の期限が90日後にリセットされ、**灯りポイント +5**。
- 期限から**さらに90日**無回答なら `dormant`。
- 過去の回答履歴はスポット詳細と確認画面に時系列で出る（例: 2025年12月 静かなまま）。

### 2.4 並び順（検索・一覧）

必ずこの優先順で並べる。

1. `quiet` のスポット（新しい確認があるものほど上）
2. `crowding`
3. `touristy`

同一ステータス内は「距離が近い順」。距離が取れない場合は「最終確認が新しい順」。

### 2.5 灯り（ポイント／バッジ）

- **灯りポイント**: 確認1回 +5、ピンが `published` になったら +10。
- **バッジ**: 「番人」（確認20回）、「冬も歩いた」（12〜2月に確認5回）、「港」（港町の街で公開ピン3件）。
  未取得バッジもグレー表示で見せる。
- 「灯りの番人 あと2件」のように、次のバッジまでの残数を出す。

## 3. データモデル（Supabase / PostgreSQL + PostGIS）

```
cities            街（札幌・小樽・函館・旭川・富良野・釧路・帯広・稚内）
  id, slug, name, name_kana, is_port, center_lat, center_lng, default_zoom

users             ユーザー（Supabase Auth と 1:1）
  id, display_name, home_city_id, resident_years, avatar_url, lantern_points, created_at

spots             店（ピン）
  id, city_id, name, address, area_name, category, lat, lng,
  status ('pending'|'published'|'dormant'|'expired'),
  quietness ('quiet'|'crowding'|'touristy'),
  reason (60字まで／なぜ自分はここへ行くのか),
  visit_frequency ('weekly'|'monthly'|'yearly'),
  author_id, photo_url,
  published_at, next_verification_at, last_verified_at, created_at

spot_tags         タグ（魚屋直営／昼が本番／現金のみ／ひとりで入れる 等）
  spot_id, tag_id

tags
  id, slug, label, kind ('accent'|'accent2'|'neutral'|'outline')

endorsements      「行ったことがある」承認（pending → published の条件）
  id, spot_id, user_id, created_at   -- UNIQUE(spot_id, user_id)

verifications     90日ごとの確認回答
  id, spot_id, user_id, answer ('quiet'|'crowding'|'touristy'), note, created_at

bookmarks         栞
  id, user_id, spot_id, planned_at (任意: 「明日 12:30」), created_at

badges / user_badges
  灯りバッジの定義と取得記録
```

### RLS 方針

- `spots`: `status='published'` は誰でも読める。`pending` は投稿者と同じ街のユーザーのみ。
- `endorsements`: 自分の行のみ挿入可。自分の投稿したスポットには挿入不可。
- `verifications`: 対象スポットの `author_id` のみ挿入可。
- `bookmarks`: 自分の行のみ読み書き可。

## 9. 監査による確定事項（2026-09-09 追補・上記に優先する）

Codex による仕様監査（`.superpowers/sdd/urasupo/codex-spec-audit.md`）と
実装後の目視検証で確定した内容。**§2〜§5 と矛盾する場合はこの §9 を採る。**

### 9.1 確認依頼（verification_request）— 新規テーブル

`/verify/[requestId]` の `requestId` はスポットIDではなく**確認依頼のID**である。

```
verification_requests
  id, spot_id, user_id(＝依頼先＝投稿者), due_at,
  status ('open'|'answered'|'missed'), answered_verification_id, created_at
```

- `published` 到達時、および回答受理時に、次の依頼を `due_at = now + 90日` で1件作る。
- 同一スポットに `open` の依頼は**常に高々1件**。
- 回答すると `answered` になり `verifications` に1行入る。
- `due_at` からさらに90日で `missed` になり、スポットは `dormant`。

### 9.2 静けさの判定 — 多数決をやめる

RLS上、確認に答えられるのは投稿者だけである。したがって多数決は成立しない。

> **現在の静けさ ＝ 最後に受理された確認の回答。確認が一度も無ければ投稿時の申告値。**

§2.1 の「多数決」は破棄する。

### 9.3 dormant からの復帰

`missed` になって `dormant` に落ちたスポットは、**投稿者が確認に答えた時点で `published` に戻る**。
この遷移は日時ベースの `nextStatus` では判定できないため、回答イベントを受ける関数を分ける。

### 9.4 期限の基準を一本化

- `VERIFICATION_INTERVAL_DAYS = 90`（公開/回答 → 次の `due_at`）
- `DORMANT_AFTER_DUE_DAYS = 90`（`due_at` を90日超過 → `missed` → `dormant`）

`DORMANT_AFTER_DAYS = 180` は**廃止**。基準は常に `due_at` からの経過日数とする。

### 9.5 並び順の完全な比較キー（§2.4 を置き換え）

```
1. 静けさ順位   quiet(0) < crowding(1) < touristy(2)
2. 距離         近い順（不明は Infinity）
3. 最終確認日時 新しい順
4. id           昇順（同値時の決定性を保証）
```

### 9.6 ポイント付与の冪等性

- 確認 +5 は **`verification_requests.id` につき一度だけ**。
- 公開 +10 は **`spots.id` につき一度だけ**（`published_at` が初めて入るときのみ）。
- Cron の再実行・回答の再送で二重加算してはならない。

### 9.7 pending の競合

- `pending` の期限は `created_at + 30日`。
- **2人目の承認が期限前に成立すれば公開が勝つ**（同時刻なら公開を優先）。
- `expired` は終端状態。以後の承認は受け付けない。

## 9.13 安全性と整合性（2026-09-14 最終レビュー領域Aの裁定・§9.1〜9.12 に優先する）

最終レビュー（Codex gpt-5.6-sol / max）で、**クライアントが Supabase の API を直接叩けば RLS の穴から
ポイント・確認履歴・承認を捏造できる**ことが判明した（`.superpowers/sdd/urasupo/final-review-A-result.md`）。
原則: **状態・時刻・ポイントを変える書き込みは、利用者に直接させない。** DB 関数（RPC）に集約し、DB が検査する。

### 9.13.1 デモモードは明示的に有効にしたときだけ
- `URASUPO_DEMO_MODE=1` を**明示**したときだけデモモード。かつ本番（`VERCEL_ENV=production` または `NODE_ENV=production`）では**無効**（設定されていたら起動時に例外）。
- Supabase の環境変数が**一部だけ**設定されている（URL はあるが anon key が無い、など）ときは例外を投げる（fail-closed）。
  「足りないからデモに落ちる」挙動は禁止。

### 9.13.2 書き込みは DB 関数（RPC）経由
以下は `security definer` の Postgres 関数にし、対象の行をロックしたうえで条件を DB が再検査する。
Server Action はこれを呼ぶだけにする。authenticated ロールからの**直接の insert/update は取り上げる**。

| 関数 | 検査すること |
|---|---|
| `create_spot` | 投稿者の `home_city_id` と投稿先の街が一致（地元の人だけ）。`status`・時刻列はDBが決める |
| `endorse_spot` | 対象が `pending` かつ期限前、投稿者本人でない、同じ街の住人。承認時刻はDBの `now()` |
| `answer_verification` | 下記 9.13.3 の回答可能条件。回答・依頼の更新・次回依頼・スポット更新・ポイントを**1トランザクション**で |
| `run_verification_cron` | service-role 専用。期限処理を行ロック下で行い、公開が期限前に成立していれば公開を優先 |

- `verifications` に `verification_request_id`（一意）を追加し、依頼を経由しない回答を不可能にする。
- `endorsements.created_at`・`spots` の状態/時刻列は DB 既定値のみ（利用者は指定できない）。

### 9.13.3 確認に回答できる時点（§9.1 の補足）
- 回答できるのは **`due_at` を過ぎた `open` の依頼**だけ（`due_at <= now`）。期限前の依頼は画面に「確認待ち」として出さない。
- **dormant からの復帰（§9.3）**: スポットが `dormant` のとき、投稿者は**最新の `missed` 依頼に1回だけ**回答できる。
  回答すると `published` に戻り、次の依頼を `now + 90日` で作る。
- 回答の受理と +5 は同じトランザクションで行い、同じ依頼では二度と受理しない（§9.6 を DB で保証）。

### 9.13.4 ポイントは台帳で管理
- `lantern_events(user_id, kind, source_id)` に `(kind, source_id)` の一意制約。確認なら `source_id = verification_request_id`、公開なら `spot_id`。
- `users.lantern_points` は台帳への記録と同じトランザクションで加算する。**利用者はこの列を更新できない**（列単位で権限を剥奪）。
- 利用者が更新できる `users` の列は、表示名・アバター・居住街・居住年数だけ。

### 9.13.5 pending の期限は絶対時刻
- `now >= created_at + interval '30 days'` で `expired`（日数の切り捨てで判定しない）。
- 2人目の承認のDB時刻が期限前なら公開が勝つ。判定はスポット行のロック下で行う。
- 期限ちょうど（`now = created_at + 30日`）の承認は期限内（§9.7 同時刻は公開優先）。DB時刻は `now()`＝各RPCのトランザクション開始時刻。

### 9.13.6 読み取りの範囲
- 未ログインでも読めるのは、公開中のスポットと、それに紐づく表示に必要な列だけ。
- `users` は表示用の列だけを出すビュー経由にする。`endorsements`・`verifications` は、読めるスポットに紐づく行か本人の行に限る。
- 表示用ビュー（`public_profiles`）と `user_badges` で見えるのは、**本人**・**公開中のスポットの投稿者**・**呼び出し者が読める pending スポットの投稿者**だけ（2026-09-16 再レビューの裁定。スポットを持たない利用者は匿名に見せない）。

### 9.13.7 その他
- メールリンクの戻り先の origin は固定の環境変数（`NEXT_PUBLIC_SITE_URL`）から作る。リクエストヘッダー（`x-forwarded-host`）は使わない。
- `CRON_SECRET` は `timingSafeEqual` で比較する。
- RLS と DB 関数には、ローカル Supabase を使った統合テスト（匿名・投稿者・同じ街・別の街・service-role の権限表、同時回答・承認と cron の競合）を置く。


### 9.13.8 権限とDB関数の書き方（2026-09-16 再レビューの裁定）
- **GRANT は既定権限に頼らず明示する**。public スキーマの全オブジェクトについて anon / authenticated から一度すべて取り上げ、必要な SELECT・栞の書き込み・RPC の EXECUTE だけを付け直す。service_role にも必要な権限を明示する。
- DB 関数は `set search_path = ''` とし、すべての名前をスキーマ修飾する（`public.spots`、`auth.uid()`）。PostGIS はマイグレーション時に実際のスキーマ（`pg_extension.extnamespace`）を調べて修飾する。public スキーマへの CREATE は anon / authenticated / PUBLIC に与えない。
- `run_verification_cron` はスポット行を `for update skip locked` で取り、ロック中のスポットは次回に回す（回答・承認と交差デッドロックしない）。cron の API は `40P01`・`40001` のとき1回だけ再実行する。
- 同時実行の統合テストは2接続（pgTAP＋dblink）で書く。
- 本番（`VERCEL_ENV=production` または `NODE_ENV=production`）の `NEXT_PUBLIC_SITE_URL` は https 必須。
- 0006 は未適用・未リリースのため、この裁定は 0006 自体を書き換えて反映する（本番DBは未作成）。

### 9.16 住んでいる街の変更（2026-09-18）

住んでいる街（`users.home_city_id`）は「ピンを立てられる街」（`create_spot`）と「地元として確認できる街」（`endorse_spot`、同じ街の2人の確認）を決める。見に行く街を選ぶだけで地元の人になれてはいけないため、次のとおりとする（§9.13 に優先する）。
1. **見る街と住んでいる街を分ける。** S1（`/start`）の「歩きはじめる」は住んでいる街を変えない。住んでいる街が未設定（NULL）のログイン利用者に限り、初回だけ選んだ街を住んでいる街にする（従来の初回設定体験は維持）。設定済みなら何もしない。
   - （R13 重要1）`/start` は「未設定か」を先に読んで判断せず、初回設定専用の DB 関数 `initialize_home_city` だけを呼ぶ（2タブが同時に NULL を読むと、後続が「1回目の変更」として成立し90日の制限までかかるため）。`/me` は `set_home_city` のまま。
2. **住んでいる街の変更は `/me` の明示的な操作だけ。** 「住んでいる街」欄（h3）に現在の街と「変更する」を置く。押すと「住んでいる街を選ぶ」（今の街を除いた街の選択）と「変える」「やめる」が出る。「変える」で確認ダイアログ「住んでいる街を◯◯に変えますか。次に変えられるのは◯年◯月◯日以降です。」（「やめる」「変える」）を出し、「変える」で確定する。
   - 成功: `role="status"` で「住んでいる街を◯◯に変えました。」。制限中は欄に「次に変えられるのは◯年◯月◯日以降です。」を添える。
   - 失敗: `role="alert"` で理由（下の拒否文言）を出す。想定外の失敗は「住んでいる街を変えられませんでした。もう一度お試しください。」。
   - 未設定の利用者の表示は「まだ決めていません」、確認は「住んでいる街を◯◯に変えますか。」（初回は制限に数えないため日付を添えない）。
   - 欄の補足「ピンを立てられるのも、地元として確認できるのも、住んでいる街だけです。住んでいる街は90日に1回まで変えられます。」
   - ボタンと選択欄の当たり判定は 44px 以上。
   - （R13 重要2、WCAG 2.4.3 / 2.4.11）確認ダイアログは `<dialog>` の `showModal()` によるモーダル（背景は操作不可、Esc で閉じる、見出しを `aria-labelledby`）。初期フォーカスは「やめる」。Tab／Shift+Tab はダイアログ内で循環する。
   - 「変える」を押したら処理中もダイアログを開いたまま、ボタンを無効にし（フォーカスを失わないよう `aria-disabled`）、`aria-busy="true"` と常設のライブリージョンで「変更しています…」を知らせる。処理中は Esc・「やめる」でも閉じない。
   - 失敗はダイアログ内に `role="alert"` で理由を出し、閉じない。閉じた後も理由は選択欄に `aria-describedby`／`aria-invalid` で結び付けて残す。
   - 閉じたら起点へフォーカスを戻す。成功は編集欄が閉じるため「変更する」、取消（失敗後の取消を含む）はダイアログを開いた「変える」。
3. **変更は90日に1回まで（DBで強制）。** `supabase/migrations/0007_home_city_change_limit.sql`:
   - `users.home_city_changed_at timestamptz` を追加（NULL = 未変更。初回設定は数えない）。`UserProfile.homeCityChangedAt` で読む。
   - `authenticated` から `users.home_city_id` の直接 INSERT / UPDATE 権限を外す。初回設定（NULL → 街）も RPC に統一する。
   - `public.set_home_city(p_city_id uuid) returns timestamptz`（security definer、`search_path = ''`、EXECUTE は authenticated だけ）。本人の users 行を `for update` でロックしてから検査する（同時に呼んでも2回は変わらない）。
     - 未ログインは「ログインが必要です」、存在しない街は「街の情報が取得できませんでした」で拒否。
     - 現在 NULL → 設定し、戻り値 NULL（`home_city_changed_at` は明示的に NULL に戻す。都市の削除などで「街だけ NULL・変更日時あり」になった行に古い制限を残さない）。同じ街 → 何もしない（記録済みの時刻を返す）。
     - 別の街 → `home_city_changed_at` が NULL か90日以上前なら変更して `now()` を記録・返す。90日以内なら「住んでいる街は90日に1回まで変えられます。次に変えられるのは◯年◯月◯日以降です。」で拒否（HINT に `next_change_at=<ISO8601>`）。
   - 「次に変えられる日」は東京の日付で表し、時刻の端数は翌日へ切り上げる（「◯日以降」がその日の0時から必ず正しいように）。
   - `public.initialize_home_city(p_city_id uuid) returns boolean`（初回設定専用。security definer、`search_path = ''`、EXECUTE は authenticated だけ）。本人の users 行を `for update` でロックし、現在 NULL のときだけ設定して true（`home_city_changed_at` は NULL）。設定済み（またはプロフィール行が無い）なら何もせず false（例外にしない）。未ログイン・存在しない街は `set_home_city` と同じ文言で拒否。
4. デモモード（フィクスチャ）も同じ規則・同じ文言を再現する（`src/lib/domain/home-city.ts`）。

### 9.17 お問い合わせ（2026-09-20、2026-09-23 最終レビュー R19 重要1・3・4・5・6、2026-09-24 R20 重要3・4・5 で改訂）

ウラスポは、実在の店を本人の許可なく地図に載せている。掲載を止めてほしいという申し出を受けられない状態で公開してはいけないため、窓口 `/contact` を置く（`/shops`・スポット詳細からも誘導する）。
1. **保存先は DB。運営へのメール通知は任意。** 受け取った内容は `public.contact_messages` に保存し、運営者が Supabase の画面（service_role）で読む。
   - `supabase/migrations/0009_contact_messages.sql`・`0010_contact_hardening.sql`・`0013_contact_privacy_requests.sql`: `id` / `created_at` / `category` / `message` / `reply_to` / `spot_id`（`spots` を参照。削除時は NULL）/ `user_agent` / `requester_id`（`auth.users` を参照。削除時は NULL）/ `status`（`new` / `in_progress` / `done`）。
   - `category` は `removal`（掲載を止めてほしい）／`correction`（内容の訂正）／`privacy`（自分の個人情報について（開示・訂正・削除・利用停止））／`other`（その他）。
2. **受け取った内容は公開しない。** RLS を有効にし、ポリシーを1つも作らず、`anon` / `authenticated` には表への select / insert / update / delete を一切与えない。読めるのは `service_role`（運営）だけ。送信元の記録 `public.contact_rate` も同じく利用者からは一切触れない。
3. **書き込みは DB 関数だけ。利用者からは直接呼べない。** `public.submit_contact_message(p_category text, p_message text, p_reply_to text, p_spot_id uuid, p_source_hash text, p_requester_id uuid, p_user_agent text) returns uuid`（security definer、`search_path = ''`、**EXECUTE は `service_role` だけ**）。Server Action がサーバー専用の service_role 接続（`SUPABASE_SERVICE_ROLE_KEY`。ブラウザには出さない）で呼ぶ。公開 RPC を直接呼んで回数制限を迂回できないようにするため（R19 重要5）。
   - 検査と拒否文言（順に）: 用件が4種以外なら「用件を選んでください」、本文が空白（全角空白・改行を含む）だけなら「お問い合わせの内容を入力してください」、2000字を超えれば「お問い合わせの内容は2000字以内で入力してください」、返信先の形が違えば「メールアドレスの形をご確認ください」、`privacy` で `requester_id` も返信先（前後の空白を除いて空でないもの）も無ければ「ログインせずに送る場合は、本人確認のため、返信用のメールアドレスを入力してください。」（0013。画面では返信先の欄の誤りとして出す）、`spot_id` が存在しない・公開中でないなら「お店の情報が取得できませんでした」。
   - 返信先メールアドレスの検査（前後の空白を除いたうえで。画面・Server Action と DB の両方）: 空白・改行・制御文字を含まない、`@` がちょうど1つ、ローカル部とドメイン部が空でない、ドメインに `.` を含む、320字以内。
   - **送信元ごとの回数制限（永続）。** 送信元は `sha256(送信元IP + CONTACT_RATE_SALT)` の16進64文字（`p_source_hash`）で表し、IP そのものは保存しない。上限は**1時間に5件・1日に20件／送信元**、全体で**1日に500件**。超えたら「しばらく時間をおいてから送ってください。」。判定と記録（`contact_rate` への1行）は RPC の中で、勧告ロックで直列化して同じトランザクションで行う。`CONTACT_RATE_SALT` が未設定なら、起動時ではなく送信時に拒否する（デモモードでは不要）。
   - **容量の上限。** `contact_messages` が全体で10,000件に達したら新規を受け付けない（同じ文言。運営が古いものを整理するまで。サーバーのログに記録する）。
   - **重複排除。** `category + message + spot_id + reply_to + requester_id + 送信元` がすべて同じ送信が直近1分以内にあれば、新しい行を作らず `null` を返す（呼び出し側は成功として扱う。回数にも数えない）。店・返信先・送信者・送信元のどれかが違えば別件として保存する（R19 重要6）。
   - **送信者の記録。** ログイン中なら Server Action が本人の ID を `requester_id` に渡す（未ログインなら NULL）。`user_agent` はブラウザの User-Agent ヘッダーを Server Action が読み取り、200字で切って渡す（R19 重要1）。
4. **個人情報の請求（`privacy`）。** 受付の経路は2つ（R20 重要3。`0013_contact_privacy_requests.sql`）。
   - **ログイン中:** そのアカウントのご本人からの請求として受け付ける（`requester_id` を保存）。返信先は任意。回答はアカウントに登録しているメールアドレス宛に送る（運営が `requester_id` から Supabase の Authentication で確かめる）。
   - **ログインできない人・退会した人:** ログインせずに送れる。返信先が**必須**で、登録している（退会した場合は、登録していた）メールアドレスを書いてもらう。運営がそのアドレス宛にメールで確認し、本人であることを確かめてから回答する。
   - DB は `privacy` で `requester_id` か返信先のどちらかを必須にする（RPC の検査。表の check 制約にはしない。`requester_id` は退会で NULL になるため、制約にすると返信先の無い請求をした利用者のアカウントを削除できなくなる）。退会後も問い合わせの行は残り（`requester_id` だけが NULL）、受付から1年を過ぎるまで請求の対象になる。
   - 画面: 未ログインで `privacy` を選ぶと、用件の下に案内（`role="alert"` にしない。`aria-live="polite"`）「ログインして送ると、そのアカウントのご本人からの請求として受け付けます。ログインできない場合や退会した場合は、返信用のメールアドレスに、登録している（退会した場合は、登録していた）メールアドレスを書いて送ってください。運営からそのアドレス宛にメールで確認し、ご本人であることを確かめてから回答します。」と「ログインする」（`/login?next=%2Fcontact`）を出し、返信先のラベルを「返信用のメールアドレス（必須）」（`aria-required="true"`。`required` 属性はブラウザ独自の吹き出しで送信を止めるため使わない）、案内を「登録している（退会した場合は、登録していた）メールアドレスをご記入ください。本人確認のため、運営からこのアドレス宛にメールで確認します。」にする。ログイン中に `privacy` を選ぶと、返信先は任意のまま、案内を「個人情報についての回答は、アカウントに登録しているメールアドレス宛にお送りします。」にする。
5. **画面 `/contact`。** h1「お問い合わせ」。用件のラジオ（上の4つの日本語ラベル）、本文（2000字まで・残り文字数を表示）、返信用のメールアドレス（任意。「返信が必要な場合だけ、ご記入ください。」）、「送る」。
   - `?spot=<id>` が付いていれば、その公開中の店を対象として表示し、hidden で送る。
   - 送信は Server Action。成功したら入力欄を閉じ、`role="status"` の中の見出し（h2、`tabIndex=-1`）「お送りしました。ありがとうございます。」へフォーカスを移す。見出しの下は、`privacy` なら「本人確認のうえ回答します。」、それ以外は「返信をお約束するものではありません。掲載停止のご連絡は、内容を確認でき次第、対応します。」（Server Action は成功の状態に用件を載せる）。失敗は `role="alert"` で理由を対象の入力欄のそばに出し、最初の不正な入力欄（用件なら選んでいる選択肢、無ければ最初の選択肢）へフォーカスを移す。想定外の失敗は「お送りできませんでした。時間をおいて、もう一度お試しください。」。
   - 二重送信は、送信中のボタンを `aria-disabled`（フォーカスを失わせない）にし、`isPending` の間の送信を無視して防ぐ。
   - 失敗しても入力（用件・本文・返信先）は消さない（JS が動いているときは送信時のフォームの自動リセットをさせない）。
   - 「返信をお約束するものではありません。ただし、ご自身の個人情報についての請求には、本人確認のうえ回答します。」「掲載停止のご連絡は、内容を確認でき次第、対応します。」を明記し、本文に個人情報を書かないよう案内する（「速やかに」は約束しない。R20 重要5）。
   - ラベルと入力を関連付け、当たり判定（送るボタンを含む）は 44px 以上（WCAG 2.2 AA）。
6. **運営への通知（任意）。** `RESEND_API_KEY` と `CONTACT_NOTIFY_TO` が両方設定されていれば、保存に成功したあと Resend の HTTP API（`POST https://api.resend.com/emails`、fetch。依存は追加しない）で運営へ短いメールを送る。本文は**用件・受付ID・受付時刻だけ**で、問い合わせの本文や返信先は載せない（メールに個人情報を流さない）。送信失敗は保存を取り消さず `console.error` に記録する。重複として保存しなかった送信は通知しない。未設定なら何もしない（`scripts/check-production-env.mjs` は警告を出す）。
7. **保存期間。** 問い合わせは**受付から1年を過ぎたあとの日次の処理**で、`contact_rate` は**24時間を過ぎたあとの日次の処理**で削除する。日次 cron（`/api/cron/verification`、`vercel.json` で1日1回）の最後に `public.purge_expired_contact_data() returns jsonb`（security definer、`search_path = ''`、EXECUTE は `service_role` だけ）を呼ぶ。削除の条件はちょうど（`created_at <= now() - interval '1 year'` / `'24 hours'`）だが、実行が1日1回のため、`contact_rate` は**最大でおよそ48時間**残る（R19 重要4、R20 重要4）。処理に失敗した日は、次の日以降の実行で削除する。利用者向けの文書（`/privacy`・`/faq`）もこの書き方にそろえ、「最大24時間」とは書かない。
8. **掲載停止の扱い。** `removal` の申し出は、内容を確認でき次第、対応する。店を地図から外すときは、**必ず §9.18-3 の `public.remove_place(p_spot_id, p_note)` を使う**（Supabase の SQL Editor で `select public.remove_place('<スポットのID>', '<メモ>');`）。`spots.status` を Table Editor などで直接変えてはいけない（掲載停止リスト `removed_places` に記録されず、同じ店の再投稿を止められない。R20 重要5）。同じ店の別の投稿（同名・100m 以内）が公開中なら、それぞれ `remove_place` で外す。対応状況は `contact_messages.status` で追う。
   - 問い合わせの確認は運営者が行い、**週1回以上** Supabase の Table Editor で `contact_messages` の `status = 'new'` を確かめる。運営への通知（6.）を設定した場合は、通知を受けたら確かめる（手順は `docs/DEPLOY.md` 4.6節）。
9. デモモード（`URASUPO_DEMO_MODE=1`）は DB を持たないため、同じ規則（検査・privacy・重複排除・保存期間）をインメモリのフィクスチャで再現するだけで、どこにも保存しない（成功表示までを確かめられる）。送信元ごと・全体の回数制限と容量の上限は再現しない。デモユーザーは常にログイン中なので、未ログインの `privacy`（返信先が無ければ拒否・あれば保存）は実DB版E2E（`e2e-realdb/contact.spec.ts`）で確かめる。

### 9.18 表示名・公開プロフィール・掲載停止リスト（2026-09-23、最終レビュー R19 重要2・重要7）

§9.13.4 の「利用者が更新できる `users` の列は、表示名・アバター・居住街・居住年数だけ」は、この節で置き換える。`supabase/migrations/0011_profile_privacy_and_removed_places.sql`（2026-09-24 の最終レビュー R20 重要1・重要2・軽微への対応は `0012_public_data_minimization.sql`）。
1. **表示名にメールアドレスの一部を使わない。**
   - ログイン時（`/auth/callback`）のプロフィール行は DB 関数 `public.ensure_user_profile() returns void`（security definer、`search_path = ''`、EXECUTE は authenticated だけ）が作る。表示名の初期値は **「地元の人」**。行があれば何もしない（表示名を上書きしない）。本人が送れる `user_metadata` も使わない。
   - 既存の利用者: マイグレーションで、`users.display_name` が `auth.users.email` の `@` より前と一致する行だけを「地元の人」に置き換える（`public.replace_email_derived_display_names()`。誰にも EXECUTE を与えない）。
   - 表示名の変更は `/me` の「表示名」だけ。DB 関数 `public.set_display_name(p_name text) returns text`（security definer、`search_path = ''`、EXECUTE は authenticated だけ）。前後の空白（全角空白・改行を含む）を除いてから検査し、保存した名前を返す。拒否文言:
     - 空: 「表示名を入力してください」
     - 21文字以上: 「表示名は20文字以内で入力してください」
     - 改行・制御文字: 「表示名に改行や制御文字は使えません」
     - メールアドレスの形（`@` または全角 `＠` の前後に空白でない文字がある）: 「表示名にメールアドレスは使えません」
     - 見えない書式文字（Unicode の一般カテゴリ Cf。U+202E などの双方向制御文字 `Bidi_Control`、ゼロ幅空白・ゼロ幅接合子、U+FEFF、タグ文字を含む）: 上と同じ「表示名に改行や制御文字は使えません」（2026-09-24、R20 軽微。`0012_public_data_minimization.sql`）。署名の見た目の偽装を防ぐ。書式文字は前後の空白を除いても残るので、空・長さより先に調べる（書式文字だけの名前も「空」ではなくこの文言）。一覧は Unicode 17.0 の Cf を範囲で持ち（`FORMAT_CHARACTER_RANGES` と DB 関数 `public.contains_format_character(text)`。誰にも EXECUTE を与えない）、テストで実行環境の Cf と照合する。ゼロ幅接合子でつなぐ絵文字（家族の絵文字など）も使えない。異体字セレクタ（U+FE0F。Cf ではない）は使える。既存の表示名に書式文字があれば、マイグレーションで「地元の人」に置き換える。
   - 同じ規則・同じ文言を `src/lib/domain/display-name.ts` にも置き、Server Action は通信の前に弾く（デモモードもこの規則でフィクスチャに保存する）。
   - 画面: 見出し「表示名」、今の名前、「表示名を変更する」→ 入力欄「新しい表示名」→「保存する」「やめる」。案内「あなたが書いた店の詳細に、署名として表示されます。20文字まで。メールアドレスは使えません。」。確認ダイアログは出さない。成功は `role="status"` で「表示名を「◯◯」に変えました。」、拒否は `role="alert"` で理由を出し、入力欄に `aria-invalid`・`aria-describedby` で結び付ける。想定外の失敗は「表示名を変えられませんでした。もう一度お試しください。」。ボタンと入力欄は 44px 以上。
2. **公開プロフィールを絞る。**
   - `public_profiles` は **`id, display_name` だけ**（0011 で `avatar_url`、2026-09-24 の 0012〈R20 重要2〉で `area_name`・`resident_years` も外した）。行の範囲は §9.13.6 のまま。
   - 店の詳細の署名は**表示名だけ**（§4 の「— 北24条に14年、Kさん」は「— Kさん」に置き換える。デモモードも同じ。`src/lib/domain/author-label.ts`）。`users.area_name`・`resident_years` は画面から入力できず公開もしないので、0012 で既存の値を NULL にした（DB 関数 `public.minimize_profile_data()` をマイグレーションで1回呼ぶ。誰にも EXECUTE を与えない）。列は残す（本人の `/me` の表示は値が無ければ出さない）。
   - `authenticated` から `users` への直接の INSERT / UPDATE 権限をすべて外す（行の作成は `ensure_user_profile`、表示名は `set_display_name`、住んでいる街は §9.16 の RPC）。`avatar_url`・`area_name`・`resident_years` は利用者が書き換えられない。将来これらを入力できるようにするときは、RPC とプライバシーポリシーを同時に更新する。
   - 誰がどの店を承認したか（`endorsements.user_id`）は公開しない。`anon` / `authenticated` の `endorsements` への SELECT は列単位（`id, spot_id, created_at`）だけにする（画面は承認の件数しか使わない。承認は `endorse_spot` だけが記録する）。
   - **確認の回答で公開するのは `id, spot_id, answer, created_at` だけ**（2026-09-24、R20 重要1。`0012_public_data_minimization.sql`）。回答者のID（`user_id`）・備考（`note`）・依頼ID（`verification_request_id`）は公開しない。`anon` / `authenticated` の `verifications` への SELECT は、表単位ではなくこの4列の列単位だけ（行の範囲は §9.13.6 の RLS のまま。service_role は表単位で読める）。回答の中身（まだ静か／混みはじめた／観光地化した）と日時は公開される。
     - 店ごとの「確認した人数」（直近の回答から24時間以内に回答した人の数）は集計 RPC `public.spot_verifier_counts(p_spot_ids uuid[]) returns table (spot_id uuid, verifier_count integer)`（security definer、`search_path = ''`、EXECUTE は anon・authenticated）。返すのは店のIDと人数だけ。数える店は spots の RLS と同じ範囲（公開中は全員／投稿者本人はどの状態でも／承認待ちは同じ街に住む人）。回答の無い店の行は返さず、アプリは 0 人とする。
     - 本人の実績（`/me` の「確認した回数」と冬の確認の数）は本人専用 RPC `public.list_my_verification_times() returns setof timestamptz`（security definer、`search_path = ''`、EXECUTE は authenticated だけ。`auth.uid()` の回答日時だけ。未ログインは「ログインが必要です」）。
     - `listVerifications`（確認画面の履歴）は公開の4列だけを読み、型 `Verification` も `id, spotId, answer, createdAt` だけにする（CONTRACT 追補）。
     - `answer_verification` の `p_note` は **500文字まで**（コードポイントで数える）。超えたら「備考は500文字以内で入力してください」（errcode 22023。記録も依頼の更新もしない）。画面は備考を送らないが、RPC を直接呼べば入れられるため。`answerVerification`（`src/lib/db/mutations.ts`）も通信の前に同じ文言で弾く。
3. **掲載停止リスト。** 店舗から掲載停止の申し出（§9.17 の `removal`）を受けて外した店を、別の利用者が再び載せられないようにする。
   - 表 `public.removed_places`（`id`、`name_normalized`、`lat`、`lng`、`removed_at`、`note`）。RLS 有効・ポリシーなし。`anon` / `authenticated` には表の権限を一切与えない。運営（service_role）が Supabase の画面から行を足す運用で、`name_normalized` には店名をそのまま入れてよい（保存時にトリガーが正規化する）。
   - 店名の正規化 `public.normalize_place_name(text)`（immutable）: NFKC（全角英数→半角、半角カナ→全角）→ 小文字 → 空白・中黒・句読点・括弧・ハイフン・引用符などの記号を除く。長音記号「ー」は残す。
   - `create_spot`（§9.13.2）は、既存の検査のあとで、**正規化した店名が一致し、かつ 100m 以内**に記録があれば「この店は掲載を控えています。」で拒否する。
   - どの経路（承認での公開・dormant からの復帰・直接の更新）でも、掲載停止の店は `published` にならない（`spots` のトリガーが同じ文言で拒否する）。
   - 運営が店を外す RPC `public.remove_place(p_spot_id uuid, p_note text) returns uuid`（security definer、`search_path = ''`、EXECUTE は service_role だけ）: スポットを `expired`（地図・一覧・承認待ちのどれにも出ない）にし、店名と位置を `removed_places` に記録し、open の確認依頼を `missed` にして閉じる。`dormant` は確認への回答で `published` に戻るため使わない。
   - 同じ店の別の投稿（同名・100m 以内）が既に公開中なら、それぞれ `remove_place` で外す（自動では外さない）。
